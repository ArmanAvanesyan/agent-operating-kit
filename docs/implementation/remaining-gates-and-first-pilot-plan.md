# Completion plan for remaining P3–P10 gates and the first P9 pilot

Date: 2026-10-24. This completes the existing ten-phase roadmap; it introduces no
additional phase. This is a plan, not a live execution, credential, provider-write
or production authorization. Existing blocked gates remain blocked until their
own evidence is accepted.

## Target and current status

The first candidate route is one local **Codex App Server + GitHub Issue comment**
route, using a disposable repository, a dedicated least-privilege account and a
standard-risk, issue-sized change. Pin the actual installed version, executable
digest, platform, authentication mode, exact catalog configuration/selector,
execution profile, account/pool, control policy, verifier and provider operation
at enrollment. Do not infer a selector from a research label. Discovery may reject
this route; it does not authorize silently switching hosts, accounts or billing.

The first end-to-end endpoint is independently accepted code, preserved local
handoff and a verified evidence comment on the enrolled issue. This is not issue
completion, merge, deployment, release or publication. A publication/delivered
claim requires its separately qualified destination and verification operation.

Current checkout evidence supports offline/injected implementations, not a
qualified live route. Codex and Claude P6 live gates are independently blocked;
live quota collectors, protected verifier/identity services, provider conformance,
actual pilot observations and production activation remain pending. The standard
CLI does not install production services merely because credentials exist.

## Implementation prerequisites that must not be mistaken for missing credentials

1. **P9 route applicability.** Readiness v1 requires all four provider gates and
   publication; only its Codex/Claude gates allow specified non-applicability.
   A GitHub-only local-handoff pilot cannot waive those v1 requirements. Integrate
   protected readiness v2 throughout the selected enrollment/admission path and
   use an exact, operation-bound milestone policy. Preserve v1 signed bytes and
   interpretation. Add route validators for acceptance, local handoff and provider
   operation; publication must be required whenever the route claims it. Universal
   identity, controls, capability, capacity, quality, verification, authorization,
   runtime and driver/platform gates remain mandatory.
2. **P9 controlled-trial coordinator.** `DispatchPilotOnce` assesses completed
   evidence and requires a promotion grant before launch. It is a promoted canary
   path, not the means to collect the first controlled campaign's evidence. Add a
   distinct externally enrolled experimental coordinator, using existing P7
   claims/fences, P3 accounting and P6 execution. Define a closed, separately
   versioned experimental record and grant with distinct digest domains, campaign
   identity and authority role. They are structurally inadmissible to production
   dispatch and promotion verification; changing a purpose string or copying a
   result cannot convert them. Experiments using ordinary selection still pass
   every P4/P3/P6/P7/P8 hard gate. A scoped experimental grant permits evidence
   collection, not production promotion; it cannot approve its own results or
   replace the later promotion assessment. Keep `DispatchPilotOnce` unchanged.
   A later production enrollment may reference independently verified historical
   experimental observations only under its explicit evidence/chronology policy,
   retaining their original purpose, dates and digests. If that policy cannot
   establish admissibility, promotion remains blocked.
3. **P4/P9 calibration execution.** Signed bounded calibration admission already
   exists, but needs a qualified purpose-specific coordinator. Keep disposable
   calibration separate from ordinary production admission. Its explicit
   non-quality guards, finite demand upper bounds, external atomic trial
   consumption and independent verification remain mandatory. Never add an
   ordinary `ignore-quality` option. Calibration enrollment does not establish
   production eligibility. Its outcomes may enter P4 only under P4's independent
   issuer, partition, exact-cohort and verifier rules.

These changes belong to P7/P9 integration and P4 evidence preparation. They are
not a new roadmap phase or permission to weaken existing gates.

Provider and verifier qualification can proceed independently of host qualification
in their own disposable scopes. Calibration may begin only after its own controls,
capability, capacity and verification guards pass; it cannot wait for production
quality evidence that it is intended to collect. Experimental trials under normal
selection must already have that quality evidence. Shadow collection can run in
parallel once frozen qualified inputs exist; promotion waits for every required
campaign and shadow result.

## P3 rollover and P4 evidence acceptance

For the first pilot, stop new admission before a relevant window boundary if an
attempt could outlive its qualified accounting scope. P3 cross-window settlement
remains fail-closed. Clock passage or a reset hint never creates usable capacity:
obtain a new authoritative observation and rerun admission. Unresolved holds stay
conservative. Separately complete generation-aware rollover/settlement only after
multi-window, delayed settlement, external consumption and crash tests establish
no double spending; otherwise report cross-window execution unsupported.

P4 claim-bearing cohorts must match configuration, profile, class, language/risk,
account scope and attempt/review protocol. Use independent families as units:

- Quality: at least 30 locked audit families and the actual one-sided 95% Wilson
  lower bound at or above the versioned standard-risk floor of 0.80. All registered
  repetitions must independently pass for a family to succeed. High risk remains
  outside the first pilot; its 0.95 floor first becomes feasible with 52 all-success
  families, and failures require more data.
- Consumption: at least 30 separate validation/calibration families, with complete worst
  registered family consumption and the finite one-sided 95% split-conformal bound
  at rank `ceil((n+1)*0.95)`. The current estimator uses `validation` consumption
  and `locked-test` quality; validation observations must strictly precede the
  locked audit. Development data is for policy development, not this estimator's
  calibration count. Missing consumption is censored, never zero. Subscription demand
  needs attributable percentage-point evidence in the same pool/window family.
- Freeze cohorts, estimates, policy and search choices before audit access, with
  protected chronology. Reject family/near-duplicate leakage, shard/receipt replay,
  altered signatures and incomplete repetitions. Do not pool across accounts or
  configurations or count repetitions as independent samples.
- Enforce quality/estimate/context validity and stricter P3 freshness at selection
  and again at admission. Refreshing an observation must not renew old outcomes.

Retain the 48-packet, six-class, grouped 24/12/12 and 288–432-attempt roadmap pilot
as the broader pipeline/abstention experiment. Its small per-class partitions do
not meet broad claim-bearing cohort requirements. The first singleton route trial
is neither that entire campaign nor statistical proof of superiority.

## First P9 end-to-end trial and stop criteria

Freeze a deterministic, small standard-risk task in a disposable Go repository;
state acceptance checks explicitly rather than extracting requirements with an
LLM. Use a fixed single-step plan, one exact candidate, concurrency one, one
attempt, empty fallback, and no resume or autonomous child agents.

1. P5 captures the enrolled issue and exact revisions; explicit mappings generate
   a validated packet and binding. A refreshed capture cannot silently change the
   enrolled assignment/input.
2. P4 records an explainable decision against frozen evidence and fresh P3 state.
   Any abstention or blocker is retained; no trial substitutes another model.
3. P7 obtains the single owner/fence and P3 reservation, revalidates current route,
   policy, revocation, budget and account identity, and durably records launch
   intent before the bounded P6 invocation.
4. Normalize/dedupe events and reconcile actual stop and usage. Ambiguous stop,
   unknown consumption or generation drift blocks onward admission/finalization.
5. P8 independently verifies the exact candidate and records acceptance; preserve
   local handoff with snapshot-bound evidence. Rejected work never advances to a
   success comment or accepted milestone.
6. Generate a reviewable comment plan. A separate protected operation grant binds
   the exact accepted evidence, repository/issue, text digest, principal, expiry
   and one-send boundary. Read support or a task packet cannot grant this authority.
7. P8 sends once through the durable outbox and obtains signed, scoped readback.
   Lost response triggers reconciliation, not automatic resend. Finalize only the
   supported local-handoff/comment milestones and retain the complete episode.

Pass requires complete hash/identity lineage, independent acceptance, settled or
explicitly conservative accounting, preserved handoff, exact comment/readback and
no unexplained effect. All attempted, failed, interrupted and abstained cases
remain in their declared denominators. A second invocation with identical logical
IDs must add no launch, consumption entry or remote comment.

The trial's cost, stop, failure and recovery observations are operational evidence,
not independent P4 quality qualification. Its record and grant authorize no later
launch or publication. Verify that experimental and calibration payloads/grants
are rejected by production dispatch and `VerifyPromotionGrant`, including relabeled
payloads, copied receipts and mismatched campaign digests. Every experimental
attempt still reruns ordinary P4 selection and fresh P3/P7 admission.

Immediately stop new admissions on any unauthorized effect, credential/privacy
leak, hard-gate bypass, unfenced launch, duplicate send, revoked authority, unknown
quota, budget breach or lost monitor/witness. Cancellation does not assert stop;
retain holds and incident state until reconciliation. Signed enrollment must set
finite campaign caps and numerical outcome/deadline thresholds before execution;
missing caps block. This plan does not invent a paid allowance or authorize spend.

Before promotion, separately drill auth/scope denial; stale/rolling quota;
cancel-without-stop; forged/revoked acceptance; verifier timeout; account/binary/
policy drift; concurrent outbox claimants; crash before/after durable intent;
response loss; partial/mismatched readback; revocation in flight; and backup/restore
with a stale clone. Snapshotting is single-store: coordinated usage/runtime/outbox
recovery needs explicit reconciliation, not an assumed atomic cross-store backup.

## Staffing, checks and reporting

Use two GPT-6 Luna-medium workers after shared contracts lock. Worker A owns host,
collector and connected conformance fixtures; worker B owns protected provider/
verifier boundaries and pilot evidence tests. The primary owns coordinator,
readiness integration, authority boundaries and final assembly. In later waves,
reuse those workers for P10 hosts versus methodology/provider/platform packages.
A separate Luna reviewer checks each integrated slice; use high reasoning for
authority/recovery changes. Test workers do not act as independent production
signers, acceptance services or human enrollment authorities.

For every implementation slice run focused tests, the full Go 1.22 suite, relevant
race/multiprocess crash tests, Python regressions/parity, kit validation, packaging
and extracted-install checks, immutable-output/privacy/tamper tests, credential-free
empty-PATH/network-denied offline smoke and six CGO-disabled release builds. Add
negative tests for route applicability, bootstrap grant confusion, trial-consumption
replay and changed-input digests. Do not describe prior passing checks as tests of
future changes. Connected/native checks run only under their exact enrollment.

Publish a digest-bound gate ledger containing owner, dependency, exact scope,
evidence/revocation references, observation/expiry, blocker, next action and
accepted status. Maintain five distinct columns: implementation, fixture
conformance, live route qualification, platform certification and production
activation. A blocked external dependency has no promised completion date.

Completion labels remain precise: P3 collector/accounting qualified for the named
source; P4 evidence sufficient or insufficient for the named cohort; P6 route
qualified or blocked; P8 operation/delivery qualified or pending; P9 first trial
completed, campaign assessed and promotion authorized as distinct milestones;
P10 optional routes independently qualified or blocked. The ten-phase roadmap is
complete only for its explicitly accepted scope, with deferred/unsupported optional
capabilities named rather than hidden behind an extra phase.
